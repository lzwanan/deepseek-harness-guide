第 1 章 · 它是什么 — 1.1

模型没有手

它只能输出一串文本。读写文件、跑命令、改代码，全部发生在 harness 里 —— 而 harness 手上唯一的原料，就是那串文本。

先把最容易含混的一件事说清：模型这个接口，接收的是「消息列表 + 工具清单」，吐出的是「一段文本流」。 它没有文件句柄，没有网络连接，没有计时器。你不能让它「打开」任何东西。

那为什么它能改你的代码？因为外面套着一层程序：它把模型的输出读进来，认出一段特殊的文本， 自己动手去做那件事，再把结果当作新的文本喂回去。这一层就是 harness。

左边那串方块是模型的全部产出。它停在虚线上，什么也不会发生 —— 直到中间那层认出其中一段长得像调用申请。动画可以拖、可以暂停；鼠标停在图上按空格也能暂停。

这一节只要记住三行
  1. 模型的输入是消息列表和工具清单，输出是文本流。没有第三种能力。
  2. 「它会用工具」是个说法，不是一个能力 —— 执行工具的是外面那层程序。
  3. 所以调试 harness 时，先分清问题出在「模型说了什么」还是「那层程序做了什么」。
自测模型在回复里写了「我已经删除了 build 目录」。build 目录真的被删了吗？

不一定。这句话本身只是一段文本。只有当这段文本里同时带了一个结构化的工具调用、 并且 harness 认出来、执行成功，目录才会真的消失。模型完全可以只是「说」它删了。

闸门：什么样的文本能变成动作

不是所有输出都会触发动作，否则模型随便说句话就能格式化硬盘。闸门只认一种结构：一个带名字和参数的工具调用。 

tool/call { name, arguments }
       name       = "read_file"          ← 必须是已注册工具里的一个
       arguments  = { path: "..." }      ← 必须过这个工具的 schema

字段示意 · 实际事件名见 packages/core/tools 与 core/agent-loop

闸门后面是一串检查：这个工具在这轮对话里可见吗、参数符合 schema 吗、当前权限允许吗。全过，才真的执行。

执行结果会被写成一条 `tool/call` 结果事件，落进 Session 日志，再作为新消息回到模型。模型看到的始终是「文件里有一百二十行」这样的文字，而不是文件本身。

这一节只要记住三行
  1. 只有结构化工具调用能穿过闸门；普通文字穿不过去，再像也不行。
  2. 穿过去之前要过三道检查：可见性、参数 schema、权限。
  3. 模型永远看不到「执行」这件事，只看到执行结果的文字版。
自测如果模型把工具名字拼错了，或者参数少了一个字段，会发生什么？

调用被拒绝，错误信息作为结果回到模型。不会执行，也不会让循环崩掉 —— 模型下一步通常会用正确参数再试一次。这正是「闸门」和「执行」分开的价值： 拒绝发生在动手之前。

边界上还有两件事：历史和约束

把「文字变动作」讲完，容易以为 harness 只是个执行器。它还得管两件模型完全管不了的事。

一是历史。模型没有记忆，每次请求都是一次性的。它之所以「记得」前面聊过什么， 是因为 harness 每次重新把整段历史装配成 prompt 再发过去。这也解释了一个反直觉的现象： 同一个回合里，工具调用越多，后面的请求越贵 —— 每一次都要把更长的历史重新送一遍。

二是约束。哪些工具这轮可见、能不能写文件、命令跑在哪个目录、要不要进沙箱， 全都是 harness 在装配请求之前就决定好的。模型看到的工具清单，是 harness 筛过的那一份。

这一节只要记住三行
  1. 「记忆」不是模型的能力，是 harness 每次重新装配 prompt 的结果。
  2. 「能做什么」也不是模型决定的，是 harness 交给它的工具清单决定的。
  3. 所以读这个仓库时，先看它怎么装配 prompt、怎么筛工具，再看它怎么跑循环。
自测为什么同一个回合里第二次请求通常比第一次贵？

因为每次请求都重新组装一次完整上下文：第一次只有用户那一句话，第二次多了模型的回复、 工具调用和工具结果。历史越长，输入 token 越多。

所以这个仓库在造什么

官方对自己的描述只有一句：Everything is a Plugin. 这不是口号，是目录结构 —— 仓库里四百多个包，几乎每一个都是可替换的一层。

循环本身在 packages/core/agent-loop，具体实现是一个叫 ReactLoopAgent 的驱动器；它不自己执行工具，而是把整批调用交给 ctx.tools.execute()； 它也不自己存历史，而是往 Session 日志里追加事件。连「用哪个模型」都是运行时查出来的。

这种拆法有一个直接后果：你几乎不会「改一个文件就让功能变了」， 但你可以在不改动核心的前提下，换掉文件系统、换掉模型、加一个拦截器。 读懂它的关键，是搞清楚「谁在什么时候调用了谁」，而不是背下某个类的字段。

后面六章各拆一个零件，顺序是从外到内：02 讲一轮对话怎么被切开， 03 讲事实写在哪，04 讲插件之间靠什么认识彼此， 05 讲工具从定义到执行要过几道手，06 讲这棵树怎么被搭起来， 07 讲哪些东西被冻结、哪些允许碎。

不想按顺序读也可以：先看 全景， 一页画出五层骨架和一次请求的八步；或者直接 上手，二十分钟跑通第一个插件。

这一节只要记住三行
  1. 这个仓库的核心主张是「一切皆插件」，目录结构就是它的论点。
  2. 循环只负责编排：装配、请求、分发、记录，四件事都不自己实现。
  3. 读源码的顺序建议是：先看事件，再看调用方，最后才看类型定义。
自测如果只允许你读一个目录来理解这个项目，读哪里？

packages/core/agent-loop。它同时碰到模型、工具、会话三边， 四个源文件就把「轮次 / 步骤 / 收件箱 / 运行时上下文」串起来了。 读完它，其他包都是它的零件。
