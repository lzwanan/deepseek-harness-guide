第 5 章 · tools — 5.1

模型看到的工具，只有四样东西

上一章讲能力怎么接上线。这一章讲接上之后，一次调用到底发生了什么 —— 因为「模型能动手」这件事的全部风险，都堆在这一层。

工具在仓库里就是一个定义对象。用 defineTool 写出来的字段不止四个： name、description、parameters、 output.schema、output.render、execute、 timeoutMs、isConcurrencySafe、projectContent、 finalizeContent，以及给 Host 本地用的两个呈现函数。

packages/core/tools/README.zh.md · 有删节

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute file path' },
    offset: { type: 'number' },
    limit: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))

但把定义投影成模型可见的 schema 时，toSchema 只挑走四样：

packages/core/tools/src/schema.ts

const { name, description, parameters, deferLoading } = definition
return {
  name,
  description,
  parameters: detached,
  ...deferLoading === true ? { deferLoading } : {},
}

就这四行，是整章的地基。execute 的函数体、output.schema 声明的输出形状、timeoutMs、两个呈现函数，一个都不跨过协议边界。 模型不知道 read_file 底下是 fs/promises 还是沙箱，也不知道它会返回什么类型 —— 它只拿到一个名字、一段说明、一份参数表。

这条投影带来两个直接后果，都跟钱和速度有关：

  • schema 是 prompt 的一部分。每次请求的固定成本与可见定义的数量成正比； 用 ctx.tools.restrict() 隐藏一个工具，等于把它整份 schema 的 token 成本从那个 agent 身上移除。
  • 顺序稳定，前缀才稳定。只要可见定义与它们的顺序不变，KV cache 就能复用；注册、卸载、或作用域限制会让复用从第一个变化的 schema token 起失效。

还有一层不那么显眼：模型的参数在执行前被校验（validateArgs）， 无效输入变成一条普通的错误结果，而不是异常。这一点决定了整章的调性 —— 在这套系统里，失败也是一种结果，不是中断。

这一节只要记住三行
  1. 跨过协议边界的只有四样：name、description、parameters、deferLoading。
  2. 可见定义越多，每轮请求的固定 token 成本越高 —— 隐藏工具是真的省钱，不只是省事。
  3. 参数先校验再执行；校验失败是结果，不是崩溃。
自测模型能不能知道某个工具的输出是什么类型？

不能。输出形状写在 output.schema 里，但投影时被丢掉了 —— 它是给注册表自己校验返回值用的，不发给模型。模型对结果的唯一认知来自 output.render 渲染出来的那几段内容。

一次调用，固定六步

调用一旦被允许进入执行器，它就走一条顺序固定、但每段都可插手的流水线。 「顺序固定」这件事比「可插手」更重要：插件可以在任意一段挂上自己的钩子，却不能改变各段的相对位置。

packages/core/tools/src/events.ts + pipeline.ts · 顺序固定

tools/pre-execute      瀑布：allow / deny / cancel / ask
  ↓ 已注册的单调守卫     只能拒，拒了没人能翻案
tools/execute          环绕分发：超时、重试、指标
  ↓ execute()          你自己的工具主体
projectContent         执行期准备好的图文内容
tools/post-execute     瀑布：接受 / 替换 / 补上下文 / 拦
  ↓ finalizeContent    最后一道只看内容的处理
tools/result           只观测，结果已冻结

第一段是审批。tools/pre-execute 是一个瀑布式钩子，每一层可以往下传（next() 等于放行），也可以直接给出允许、拒绝、取消，或者「问一下」。最后那个值得单独说： 如果部署里没有审批能力，ask 会被当成拒绝，而不是当成放行。

第二段是守卫，它只能往一个方向走。ctx.tools.guard() 注册的策略排在瀑布之后，返回理由就拒绝调用，而且后续监听器没有办法把拒绝重新变成允许。 这是刻意的：审批可以是多轮协商的，安全边界不行。

第三段是环绕分发。tools/execute 包在外层，用来做超时、重试、指标。 它能改的东西被收得很紧 —— 只能换 exec.signal，而注册表在进主体之前会把调用方原本的 signal 重新融回去。换句话说，包装层没法把调用方的取消权利偷走。

然后是主体、内容、后置策略、最终结果。projectContent 装执行期准备好的内容；tools/post-execute 可以接受、替换、补上下文、或者拦掉； finalizeContent 是最后一道只看内容的处理；tools/result 只能观测，因为那时结果已经冻结了。

这套顺序买到的东西是互不相识：权限钩子不知道有超时包装层，超时包装层不知道审计钩子在记什么。 它们都只认识那几个事件和那几个决策类型。

源码里还留着一条明确的设计拒绝，很能说明这层的价值观：tools/pre-execute 有意不允许改写 exec.arguments。理由是 —— 一旦允许，日志里记的参数、界面上呈现的参数，就会跟实际跑的东西对不上。 宁可少一种能力，也不要一个会说谎的日志。

这一节只要记住三行
  1. 六段顺序固定：pre-execute → 守卫 → execute → 主体 → post-execute → result。
  2. 守卫是单调的：能拒，不能翻案。没有审批能力时，ask 等于拒绝。
  3. 钩子之间互不认识 —— 它们只认识事件和决策类型，这是顺序固定换来的。
自测为什么安全策略要做成「守卫」，而不是再写一个 pre-execute 钩子？

因为瀑布是可以协商的：后面的层能覆盖前面的决定。安全策略需要的正好相反 —— 一旦判定为危险，任何后来者都不能把它改回允许。位置（排在瀑布之后） 和语义（单调）两件事一起，才保证了这个性质。

一批调用怎么排

一个 step 里，模型可以一次吐出好几个调用。执行器拿到的不是「一次调用」，是整批 —— 所以它必须先回答一个问题：这些调用里，谁能跟谁同时跑。

答案来自定义里一个可选函数 isConcurrencySafe(args)：返回 true 的进并行组，返回 false 的构成屏障（exclusive）—— 它前面所有调用必须结算完它才开始，它没结束后面谁也进不来。 注意这个函数拿得到参数，所以同一个工具可以对不同参数给不同答案。

并行组不是「全都同时跑」，而是一个有界滚动池：上限来自 maxParallelToolCalls，默认 10，设成 1 就是串行，传非正整数会直接抛 RangeError。位子空出来一个，后面的才补进去一个。

五条横条是五次调用，横向是时间。看两处：③ 的起点正好压在 ② 的终点上（位子刚空出来）， ④ 两侧的虚线穿过所有泳道（屏障）。再对比最下面那排槽位 —— 它不看完成时间，只按模型写的序号。

图里还有一件没画出来、但源码里明确写了的事：开始之前还会重新分类一次。 如果并行组跑着跑着冒出一个独占调用，它得等当前池子排空；反过来，独占调用也不会因为它后面还有并行的就提前放行。

至于乱序，收口收在这里：派发可以在时钟上重叠，但策略、结果、结果上下文的顺序永远按模型发出的顺序。 模型看到的永远是 ①②③④⑤，它没有「并发」这个概念，也不需要。

中止时的处理也很讲究：停止补位、等已经开始的工作跑完、给被跳过的调用补一条有序的错误结果。 为什么非要补？因为日志要能回放 —— 缺一条结果的批次，回放时是断的。

这一节只要记住三行
  1. 并行与独占由定义上的 isConcurrencySafe(args) 决定，不是由工具名决定。
  2. 并行组是有界滚动池（默认 10），不是无限并发；独占调用是一道前后都等的屏障。
  3. 派发可以重叠，回填顺序永远是模型的顺序 —— 中止时连跳过的调用也要补结果，否则回放会断。
自测把 maxParallelToolCalls 调成 1 会发生什么？

并行组退化成串行：池子里只有一个位子，一次只能进一个。但屏障还是屏障， 顺序也还是模型顺序 —— 变的只是重叠程度，不变的是语义。所以这个值可以当性能旋钮拧， 不会改变任何可观察的结果。

出错不是结束

这是整套设计里最容易被低估的一条：工具调用失败，不会结束回合。 名字找不到、参数不合 schema、主体抛异常、被策略拒掉、超时 —— 全部变成一条结果，交回模型。

packages/core/tools/src/contracts.ts · 几个会出现的错误码

UNKNOWN_TOOL                 名字不在这个 agent 的可见集合里
ABORTED_BEFORE_DISPATCH      还没进主体就被取消
ABORTED                      主体跑完了才取消，成功结果被替换
TOOL_TIMEOUT                 包装层设的截止时间到了

它们在模型眼里长什么样？统一是 Error: <message> 一行。 而结构化的失败详情（name / code / reason） 会保留在持久投影里，但不进入模型内容 —— 给机器看的给机器，给模型看的只有一句人话。

前面提过取消是协作式的：工具主体会收到 exec.signal，它必须观测。 这个「必须」不是礼貌用语，而是整套超时机制成立的前提 —— 因为这里没有强制中断， 只有一个请求停止的信号。

最能说明这一点的，是 timeoutMs 的真实处境。定义上写着它，看起来像是框架会执行截止时间， 但注册表的源码里写得很清楚：timeoutMs 仅作声明之用，注册表绝不会强制执行。 真正让它生效的是另一个包 —— packages/guard/timeout-policy， 一个挂在 tools/execute 上的包装层，在 exec.signal 上装表，赢了就返回 TOOL_TIMEOUT。

而那个包的文档自己就把局限写明白了：它无法硬性停止下游工作。 一个忽略取消的工具，仍然会让调用方一直等下去。这不是没做完，这是协作式取消的固有代价 —— 要能强行杀，就得让工具跑在能被杀的进程里，而那件事属于沙箱，不属于注册表。

这一节只要记住三行
  1. 任何失败都是一条结果，回合继续 —— 否则模型没法「看到错误再改」。
  2. 模型只看到 Error: … 一行；结构化详情留在持久层，不给模型。
  3. timeoutMs 只是声明，真正执行它的是 guard/timeout-policy，而且只能请求停止，不能强杀。
自测工具主体抛了一个异常，这段代码应该写在哪一层？

随便哪一层都能兜住，但要看你想要什么：写在主体里，你能给出最具体的错误文案； 交给注册表，它会把异常规范化成结构化错误（isError），模型看到 Error: …； 想在出错后再补一句「试试别的路径」，那是 tools/post-execute 的活。 能兜住不等于应该兜住 —— 越靠后兜，能带的信息越少。
