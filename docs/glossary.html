术语表 / glossary

这些词，一句话说清

正文里带虚线的词，悬停就能看到解释。 这一页把它们集中起来，方便回头查、也方便对照源码里的命名。

01 / 基本结构 5 条
  • harness 套在模型外面的那层程序。模型只输出文字，harness 负责把文字变成读文件、跑命令、改代码这些真实动作，并把全过程记下来。本站讲的就是这一层。 全书
  • model 只做一件事：给定上下文，预测接下来的 token。它没有手，不能读文件、不能执行命令，也不会自己记住上一步干了什么——记忆是 harness 喂给它的。 01 · 它是什么
  • token 模型处理文本的最小单位。一个汉字大约 1–2 个 token，一个英文单词大约 1 个。上下文长度、费用、流式输出的速度，都按 token 计算而不是按字数。 02 · 一次请求
  • prompt 每次请求发给模型的完整输入。包括系统提示、历史消息、工具清单。关键点是它每次都要重新装配——不是一份一直存在的对话记录。 02 · 一次请求
  • context 模型这一次能看到的全部内容。它是一次性的、有上限的。超过窗口就得裁剪或摘要，这也解释了为什么长会话会「忘事」。 02 · 一次请求
02 / 循环与生命周期 5 条
  • turn 一个回合。从你按下回车开始，到模型表示「没有更多要做的」为止。一个 turn 里可以包含 0 到多个 step。它不是「一问一答」，而是「一次输入引发的全部工作」。 02 · 2.2
  • step 一步，等于一次模型请求。装配 prompt → 请求 → 可能调用工具 → 收尾。连续调三次工具，就是三个 step、一个 turn。 02 · 2.1
  • tool call 模型说「我要调用某个工具」的那句话。模型本身不执行，它只是输出一个结构化的意图；真正跑的是 harness 里的工具层，结果再回给模型。 02 · 2.3
  • loop turn 内部那个「请求 → 执行 → 再请求」的圈。它决定这个回合还要不要再问一次模型。出口只有一个：没有工具要跑，且没有新输入。 02 · 2.3
  • agent/pre-step 每个 step 开始前的一个插口。系统提示、工具清单、历史消息在这一刻被拼成这次请求。想给模型「临时补一句上下文」，通常挂在这里。 02 · 2.1
03 / 记忆与日志 4 条
  • session 一次会话的全部记录。它不是一段聊天文本，而是一串带顺序的事件。聊天的样子是从这串事件「渲染」出来的。 03 · Session 日志
  • event 日志里的一条结构化记录。用户说话、模型吐字、工具执行、回合结束，各是一条事件。带类型、带顺序、带负载。 03 · Session 日志
  • append-only 只往后写，不修改已有记录。好处是任何时刻的状态都能被重算出来，坏处是格式一旦定错，只能靠迁移追加修正——这也是它敢做破坏性变更的底气。 03 · Session 日志
  • replay 把事件按顺序再放一遍。用来复现一次会话、调试 agent 的判断，或者验证改动前后的行为差异。前提就是日志只追加。 03 · Session 日志
  • surface / 表面 从日志投影出来、模型真正看得见的那一层。日志是事实，surface 是视图： 只由五种消息事件构成，每次请求前现算。压缩改的是它，不是日志。 03 · Session 日志
  • compaction / 压缩 上下文快满时，把较早的历史换成一条摘要。它在日志里是一条 replace 事件，把被摘要的条目从「模型可见」这一层遮蔽掉——原记录仍然保留，所以之后还能 fork 回去。 03 · Session 日志
  • fork 从一个会话的精确前缀长出另一条会话。复制的是事件前缀，不是「当前状态」—— 所以父会话之后发生的事不会跟过来，未闭合的工具调用还会被补上一条恢复结果。 03 · Session 日志
  • KV cache 模型服务缓存「相同前缀」的计算结果，命中就不重算。这就是为什么只追加的日志更省： 历史越长，前缀越能复用。压缩一旦发生，从第一条被遮蔽的消息起，缓存全部失效。 03 · Session 日志
04 / 插件与组装 6 条
  • ctx 插件拿到的上下文对象。工具、模型、文件系统这些服务都挂在它上面。插件通过它注册能力、取用别人的能力，也通过它声明卸载时该回收什么。 04 · 插件模型
  • plugin 一个可以装上、也可以拔掉的单元。装上时向 ctx 注册服务，拔掉时释放自己占的东西。dsh 的几百个包，基本都是插件。 04 · 插件模型
  • provider 某个能力的具体实现。比如 fs provider 决定文件读写是走本地磁盘还是走远程沙箱。换掉它，依赖它的工具会一起换掉。 05 · 能力缝
  • seam / 能力缝 接口 + 实现 + 消费者，三件套才算一条缝。有了缝，才能只换中间那块而不动两端。没有缝的地方，任何改动都会变成一个全局搜索任务。 05 · 能力缝
  • bundle 把一组插件打包成可复用的组合。装上就得到一整套能力，不用一个个手动注册。换 bundle 相当于换一个产品形态。 06 · 组装
  • dispose 插件被卸载时的清理动作。关掉监听、释放句柄、移除注册的键。写插件最容易漏的一步——漏了不会立刻报错，只会在热重载时积累成越来越慢。 04 · 插件模型
  • cordis 底座的插件运行时。提供共享的 ctx、按键注册的服务、以及 inject 依赖声明。仓库六十多个包都活在它的装载/卸载生命周期里。 04 · 插件模型
  • inject 插件声明「我需要哪些服务键」。键还没就位时，插件装载会挂起等待而不是报错 —— 所以装载顺序不敏感，依赖关系一目了然。 04 · 插件模型

没有匹配的术语。换个词试试，中英文都行。
