全景 / overview

不是一个 Agent 程序，是插件运行时

这一页不讲细节，只回答三个问题：dsh 为什么长成这样、它的骨架分几层、一次请求怎么走完。 读完再去读任何一章，你都知道那一段在整张图的哪个位置。

官方对自己只有一句话：Everything is a Plugin。很多人把它读成「模块化做得不错」， 其实它是一个应急决定 —— 这套东西要对付的三样东西一直在变，而且变得比彼此快。

在变的东西 变化的样子 如果写死在主干里
模型 换厂商、换上下文长度、换推理档位 换一次模型就要改循环
工具 读写文件、跑命令、搜索、子代理、LSP…每周都在加 每加一个能力都要动核心
形态 Web UI、无头批处理、SDK、桌面、编辑器协议 五种外壳各写一套内核

所以它的答案不是「写一个更好的 agent」，而是只写运行时，把其余全部做成插件： 循环、工具表、日志、提示词装配、模型适配器 —— 连「用哪个模型」都是运行时查出来的。 仓库里四百多个包，几乎每一个都可以从配置里换掉。

这一刻的代价要记住：你几乎不会「改一个文件就让功能变了」。 但它换回来的是「不动核心就能换掉文件系统、换掉模型、插一个拦截器」。 后面七章讲的每一件事，都是这句话的展开。

骨架：五层，一条总线

从上往下看：最上面是你选的那种形态，最下面是它真正碰得到的世界。中间三层是 dsh 自己。

虚线框是可替换的层，实线是骨架。内核右下那格虚线空位不是遗漏 —— 它标着「文件 · shell · 沙箱」都在下一层：内核一个都不实现，它们全是能被换掉的插件。

这张图和一般的分层图有一处不同：没有中心调度器。 内核的五个模块之间不互相调用，它们都挂在同一个 ctx 上， 靠服务（按键取用）和事件（广播）打交道。 所以你可以只替换其中一个，而不动其余四个 —— 这就是「一切皆插件」在架构上的实际含义。

一次请求的八步

骨架是静态的，流程是动态的。下面这条线是你按下回车之后真正发生的事， 每一步都标了由谁负责、在哪一章展开。

  1. 01 输入被写成一条事实 你说的话不是「传给模型的参数」，而是一条 user/message 追加进日志。 从此它可回放、可 fork、可崩溃恢复。 03 →
  2. 02 循环领走它，开一个 turn turn 从领到首条输入开始，到「不再欠任何工作」结束。一个 turn 里可以有零个或多个 step。 02 →
  3. 03 装配这一次的请求 系统提示 + 由日志投影出来的历史 + 这一轮可见的工具清单，拼成一次请求。 每个 step 都重拼一次 —— 这是「越聊越贵」的根源。 05 →
  4. 04 流式请求模型 token 一个个回来。这一步只产生文本，不产生任何副作用 —— 模型没有手这件事，在这里体现得最直接。 01 →
  5. 05 输出里出现结构化调用，过闸门 只有「带名字和参数的工具调用」能变成动作。普通文字再像也不行 —— 否则模型随口一句就能删库。 01 →
  6. 06 六步流水线执行 校验 → 挂钩子 → 审批 → 守门 → 执行 → 归一。失败不会让循环崩掉： 错误本身就是一条结果。 05 →
  7. 07 结果落盘，回到下一步 tool/result 写进日志，再被投影成一条消息进入下一次装配。 模型看到的始终是「文件里有一百二十行」，不是文件本身。 03 →
  8. 08 不再要工具，写 step/end 模型这轮没再调工具，循环写一条 step/end，turn 关闭。 整个过程在日志里变成十几条只增不改的记录。 02 →

第 03 到第 08 步会循环很多次。一次「读三个文件然后改一处」的请求， 大概会走三轮：读 → 读 → 读 → 改。每一轮都重新装配一遍完整的上下文。

这也解释了一个新手最容易误判的地方：你在 UI 上看到的一段「思考」，在日志里是十几条记录。 想调试，就去读日志，不要盯着界面猜。

三种读法

同一套材料，三种人能拿到三种东西。左栏给了三组入口，这里说清每组的目标。

产品 / 决策

你要回答的是「为什么不用一个单体程序」。答案在这一页的上半段，和 第 07 章：只有日志格式被冻结，其余全部允许破坏性变更 —— 因为变化速率不同，稳定性预算只能花在一处。

架构 / 连接

你要能白板画出这张五层图，并说清「模块之间不互相调用」。 然后读 第 04 章（ctx / 服务 / 三角色）与 第 06 章（四层 patch 怎么叠出配置树）。

研发 / 动手

你要能加一个工具、改一个策略、读懂一次失败。 先照 上手 跑通第一个插件，再按 02 → 05 → 03 的顺序读。

读完能回答这八个问题吗

这八问就是本导读的验收标准。答不上来的那一条，就是你还没读的那一章。

01模型能直接改你的文件吗？它凭什么「动手」？

不能。模型只输出文本。执行的是外面那层程序 —— 它认出一段结构化的工具调用， 自己做那件事，再把结果的文本版喂回去。第 01 章

02同一个回合里，第几次请求最贵？为什么？

最后一次。每次请求都要重新装配完整上下文：系统提示、全部历史、工具清单。 历史越长，输入 token 越多。第 02 章

03日志和「模型看到的历史」是同一个东西吗？

不是。日志是只增的事实流；历史是每次请求前从日志投影出来的视图。 压缩只让视图塌下去，日志一条都不会少。第 03 章

04两个插件互相不知道对方的存在，怎么协作？

通过 ctx 上的键。一个把实现注册成 ctx.shell， 另一个声明 inject: ['shell']。换掉前者，后者一行不用改。 第 04 章

05模型看到的工具表和源码里的工具定义，差在哪？

模型只看到名字、说明、参数表。执行函数、输出形状、UI 卡片都不发给它 —— 这是一次投影，不是一份拷贝。第 05 章

06一次工具调用失败，会不会把整个 agent 弄崩？

不会。失败被收敛成一条 isError 的结果事件回到模型， 模型下一步通常会改参数重试。只有必填条目起不来才会拆掉整个应用。 第 05 章

07我想改一个默认值，该改哪一层配置？

看这个值的变化速率：跟版本走改组合包，跟项目走改 profile，跟人走改 home 级 patch。 改完用 --dump-config 确认，别靠读文件猜。 第 06 章

08为什么内部 API 可以随便改，日志格式却四代不许动？

因为只有日志会离开进程、被另一个版本的进程读到。API 的错能通知、能重跑； 日志的错意味着用户三个月前那次对话打不开了。 第 07 章
