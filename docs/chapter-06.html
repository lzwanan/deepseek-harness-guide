第 6 章 · profile — 6.1

一个 profile 是一叠补丁

前五章讲的都是「一个已经跑起来的 dsh」内部怎么运作。这一章回答之前那个问题：那棵配置树是谁搭起来的。

最容易搞错的假设是「有一个默认配置文件，你改它」。真实的模型是反的： 没有任何一份文件是完整的。一个 profile 由若干组合包（bundle）加它自己的 patch 叠出来，每个组合包只声明「我要插入这些行」。

组合包在 package.json 里用 dsh.bundle.patch 指向一个 patch 文件，或者一个有序的文件列表； 启动器按顺序把这些文档叠起来。随发行版交付的有六个： base、web-app、headless、acp-app、sdk-app、sdk-minimal。 前四个 profile 都以 base 为底，只有 sdk-minimal 例外 —— 它自带一整棵树。

右侧只看两件事：行是累加的，值却可能被覆盖。最后一层落下时没有新增任何一行 —— 它只把 sandbox-policy 的 mode 换成了别的。这就是「替换」的全部样子。

四层的顺序是固定的，而且顺序本身就是语义：后应用的那层优先级更高。

  • 组合包层——先是 base，再叠模式层（web-app 之类）。这一层随版本发布，你改不到它。
  • profile 自己的 cordis.patch.yml——在 $DSH_HOME/profiles/<name>/ 下，随安装走。
  • home 级 cordis.patch.yml——放在 harness home 里，最后应用，压过前面所有层。

之所以值得这样拆，是因为这三层的变化速率完全不同：包随版本走，profile 随项目走，home 级随人走。 如果只有一份文件，升级就会覆盖掉后两者的改动 —— 这不是洁癖，是升级能不能做的问题。

这一节只要记住三行
  1. 没有一份「完整配置」；profile 是多份 patch 文档叠出来的结果。
  2. 组合包用 dsh.bundle.patch 声明自己那一片，可以是一个文件或一个有序列表。
  3. 顺序即优先级：base → 模式层 → profile → home，最后一层压过前面全部。
自测你想给所有项目统一加一个钩子，又不想每次升级都被覆盖，补丁该写在哪一层？

写进 home 级 cordis.patch.yml。它不属于任何包，升级时不会被覆盖； 又排在最后应用，能压过 profile 与组合包的设置。反过来，如果你想让某一条只在某个 profile 里生效， 就写在那一个 profile 自己的 patch 里 —— 换 profile 就不带过去。

最小那棵树长什么样

概念讲完，看真东西。sdk-minimal 是唯一不叠 base 的 profile —— 它的 cordis.patch.yml 里那个 insert: 就是整棵树，179 行。 想理解「一个 harness 至少要什么」，读它最快。

packages/bundle/sdk-minimal/cordis.patch.yml · 有删节

# 这个 insert 就是完整配置树，不叠 dsh-base
- insert:
    - id: sdk-app-startup
      name: '@deepseek-ai/dsh-sdk-app'
      config: { profile: sdk-minimal }

    - id: sdk-jsonrpc-server
      name: '@deepseek-ai/dsh-sdk-jsonrpc-server'
      inject: [sdkAppStartup, loader]

    - id: llm-deepseek
      name: '@deepseek-ai/dsh-llm-deepseek-api-key'
      config:
        apiKeyEnv: DEEPSEEK_API_KEY
        defaultContextWindow: 1000000

    - id: sandbox-policy
      name: '@deepseek-ai/dsh-sandbox-policy'
      config:
        mode: danger-full-access
        workspaceRoot: !!js process.cwd()

    - id: terminal-bash
      name: '@deepseek-ai/dsh-terminal-bash'
      disabled: !!js process.platform === 'win32'
      config: { timeoutMs: 300000 }

把 179 行按职责分四段，就会发现它其实很朴素：

  • 外壳——sdk-app 加 sdk-jsonrpc-server。它们决定「这是个 SDK，用 JSON-RPC 说话」，是这个 profile 存在的理由。
  • 模型与日志——llm-deepseek 从 DEEPSEEK_API_KEY 取凭据；session 加 session-persistence-jsonl，而且明确写着 compression: none（存未压缩 JSONL，方便人工查看）。
  • 手和地——sandbox、filesystem、subprocess、pty、terminal-bash。最后一行用 disabled: !!js 按平台二选一，Linux/macOS 走 bash，Windows 走 pwsh。
  • 内核——timer、llm、session、system-prompt、tools、tool-executor-native、agent、agent-loop。前五章讲的所有东西，就是这八行。

它对「最小」的理解不是「少写几行」，而是每一行都自己拥有： 注释里写得很直接 —— 不像 dsh-base，这个 profile 自己拥有每个服务行，并且省略所有它用不到的可选生产者。 所以里面没有 settings、没有遥测、没有 subagent、没有 workspace 指令。

这一节只要记住三行
  1. sdk-minimal 的 insert: 就是整棵树 —— 不叠 base，是理解「最小」的最好样本。
  2. 四段职责：外壳、模型与日志、手和地、内核；前五章的内容全在最后那八行里。
  3. 「最小」的意思是自己拥有每一行、而不是删掉几行 —— 省掉的是用不到的可选生产者。
自测为什么这个 profile 要把 compression 显式设成 none？

因为它要给人看。压缩后的日志是给模型省上下文用的，不是给人排查用的； 一个「极简、显式」的 profile 宁可让文件大一点，也要让 tail -f 出来的每一行都能直接读懂。 这也侧面说明：持久化策略是配置，不是硬编码。

一行一行怎么读

树里的每个节点都是一个对象，字段只有五个： id、name、inject、config、disabled。 前两个是身份，中间那个是依赖，后两个是行为。

id 是这一行在这张表里的名字，patch 靠它定位；name 才是包。 两者分开的好处是同一个包可以装两次、配两套参数 —— 上面那段配置里 terminal-bash 就出现了两行，一个 bash 一个 pwsh，靠 disabled 二选一。

inject 就是第 04 章那个 inject，只是写在配置里： inject: [sdkAppStartup, loader] 表示「这两个服务没就位之前别启动我」。 所以行的先后顺序基本不需要你操心，依赖关系写清楚就够了。

真正要小心的是 config 的替换语义。patch 对已有条目做的是整条替换，不是深合并 —— 官方文档把括号写在里面：替换某个条目的整个配置（重述你要保留的字段）。 于是有了一个很常见的坑：

同一个 config，两种写法，后果不同

# base 里是：{ applyPatch: false, maxBytes: 65536 }
- id: tool-fs
  config:
    applyPatch: true          # ← 只写这一行

# 结果不是「改一个字段」，而是整个 config 变成 { applyPatch: true }
# maxBytes 悄悄回到了插件自己的默认值。要保留就得重述：
- id: tool-fs
  config:
    applyPatch: true
    maxBytes: 65536

还有一个只有踩过才知道的坑：空的 patch 文件会让启动失败。 不是「没有改动」的意思 —— 如果你真想禁用这一层，写 []。 反方向的容错则宽松得多：patch 指定的条目不存在，只在 stderr 上警告一句，不拦启动。

想知道自己到底装出了什么，别靠读文件、也别靠猜，用 --dump-config：它把合并后的条目原样打印出来，并且按注释分组标明每个源文件及其 patch 层。 这才是唯一可信的「最终生效配置」——你看到的顺序，就是启动器应用的顺序。

这一节只要记住三行
  1. 一行五个字段：id（表内身份）、name（包）、inject、config、disabled。
  2. patch 对已有条目是整条替换，不是深合并 —— 不重述的字段会退回默认值。
  3. 空 patch 文件会导致启动失败（禁用该层要写 []）；条目不存在只警告。
自测两个组合包都想改 system-prompt 的配置，谁会赢？

后应用的那个。组合包层按声明顺序依次叠加，后一层对同一条目的 config 做整条替换。 这也是为什么「顺序即优先级」这句话要记牢 —— 但它只对同一层里的兄弟和后叠的层成立， 不适用于依赖关系：依赖由 inject 管，跟先后无关。

起不来的时候

组装最容易出问题的地方不是写错配置，而是装了一半。这套启动器对「一半」的处理分得很细。

先分两类失败。插件装了但启动失败（抛异常），只产生一句带标签的警告，其余照常启动； 只有必填条目失败才会拆掉整个应用、以非零码退出。必填清单是写死的： agent-loop、tool-executor-native、tool-executor-ptc，加上各应用自己的入口 （webserver、headless-runner、acp、sdk-jsonrpc-server 之类）。 换句话说：能少一个工具，不能少循环。

再分两处出错。组合包读不出来（解析失败、平台不符、版本不兼容），会被跳过并记进 skippedBundles，其余组合包保持原顺序继续；但 profile 自己的 patch 或 home 级 patch 出错， 启动直接失败。这个区别是有道理的：组合包是别人的东西，坏一个不该连累全部； patch 是你的东西，坏了就说明你的意图没被表达出来，硬启反而更危险。

还有一个版本门槛。导入插件前，启动器会把它声明的 DSH 版本要求跟当前运行时比一次： 清单写了 engines.dsh 就只看这个范围，否则检查 peerDependencies 里所有 @deepseek-ai/dsh*。不匹配的组合包会被跳过并报告包名与版本。文档里有一句话值得记住 —— 这些检查不是防范恶意包代码的沙箱，它只保证版本对得上，不保证代码安全。

最后一点，也是最容易被忽略的：skippedBundles 只说明「这层没装上」， 不保证剩下的组合仍然能提供所需服务。跳过之后应用还可能因为缺服务而失败， 只是失败点挪到了后面 —— 所以看到 skip 时，别当成无害的提示。

这一节只要记住三行
  1. 插件启动失败只警告；必填条目失败才拆整个应用 —— 能少一个工具，不能少循环。
  2. 组合包坏了会被跳过并记进 skippedBundles；你的 patch 坏了直接启动失败。
  3. 版本检查只保证版本对得上，不是安全沙箱；skip 也不保证剩下的还能跑。
自测启动日志里出现一条 skippedBundles，应用却正常起来了。要不要管？

要管。应用能起来只说明必填条目还在；被跳过那一层本来要提供的东西，可能是一个工具、 一个服务、一段提示词。它不会报错，只会安静地少一块能力。 查法很直接：看被跳过包声明的 dsh.bundle.patch 里有没有你正在用的条目。
