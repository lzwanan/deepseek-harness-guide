第 3 章 · Session 日志 — 3.1

先写下来，再谈别的

模型没有记忆。harness 之所以看起来记得住，是因为它把发生过的事一条条写进了日志 —— 而「记忆」只是这份日志算出来的一个视图。

这个包叫 dsh-session，它做的事只有一件：维护一条只追加的事件日志。 会话里发生的每件事 —— 用户说了话、模型回了话、工具被调用、上下文被压缩、标题被改 —— 都是日志里的一行。没有「修改某一行」，也没有「删除某一行」，要表达变化，就再追加一条。

packages/core/session/src/types.ts

type:  'user/message'              // 事件类型，词汇表里的一种
seq:   7                          // 会话内单调递增，没有空洞
time:  1730953200000              // Unix epoch 毫秒
data:  { role, content, source }  // 该类型自己的载荷
ignorable?: true                  // 不认识的类型，能不能安全跳过

词汇表里有 60 多种事件（KNOWN_SESSION_EVENT_TYPES）。 但只有五种会变成模型看得见的消息：system/message、 developer/message、user/message、 assistant/message、tool/result。其余五十多种都是记录 —— 这一步开没开、工具调用了几次、压缩发生在第几轮。

追加不是随便塞。每条事件进来时，先做一次 无损 JSON 快照 并冻结，再检查写权限，最后才提交、通知观察者。BigInt、循环引用、稀疏数组、-0 这类存不住原样的值，会在追加这一步就被拒绝 —— 而不是等到落盘时才发现。

这一节只要记住三行
  1. Session 是一条只追加的事件日志，seq 单调递增，没有改和删两个操作。
  2. 六十多种事件里只有五种会变成消息；日志比对话长，是常态而不是异常。
  3. 追加前会做无损 JSON 快照 —— 写不进去的值在入口就被挡住，不会流到存储层。
自测事件里能不能塞一个 Date 对象？

不能。日志只接受无损 JSON，Date 会被转成字符串或直接拒绝 —— 因为「读回来和写进去不是同一个值」的记录，会让重建出来的历史不可信。时间统一用 time 这个 epoch 毫秒字段表达。

模型看到的是派生出来的

模型不读日志。每次请求之前，harness 把日志投影成一份消息数组，这份投影才是模型看到的「历史」。 投影的入口是 deriveMessages()：增量、带缓存、每次返回一个新数组。

哪条事件能进这份历史，由一个叫 surfaceOp 的字段决定。它只有两种取值： 接在尾部，或者遮蔽一段。压缩就是后者 —— 这也是为什么压缩之后模型「忘了」前半段， 而日志里那些条目一条都没少。

左列是日志，右列是模型历史。注意两件事：八条事件只产出四条消息；压缩之后右边塌成两行，左边一条没少。 拖到 ④ 那一帧，看得最清楚。

packages/core/session/src/types.ts · SurfaceOp

// 追加：接在表面尾部 —— 日常的用户 / 模型 / 工具消息都走这条
{ surfaceOp: 'append' }

// 替换：遮蔽表面上 0…4 这一段（两个端点都包含）
{ surfaceOp: { op: 'replace', startSeq: 0, endSeq: 4 } }

替换有一条硬规矩：新节点必须用 sourceEventSeqs 把被遮蔽的每一个节点都列出来。 少列一个，这条追加会被直接拒绝。这样做的原因是审计 —— 任何一条被隐藏的消息，都能顺着引用找到它原来在哪。

代价是双向的。好处是 token 立刻少了；坏处是 KV cache 从第一条被遮蔽的消息起失效 —— 前缀变了，后面的计算全要重来。会话表面只追加时前缀永远可复用， 一旦压缩，这一次的省 token 要拿一次重新计算来换。

这一节只要记住三行
  1. deriveMessages() 每次从日志投影历史：日志是事实，历史是视图。
  2. surfaceOp 只有两种：append 接尾部，replace 遮蔽一段。
  3. 压缩是 replace 的生产者：模型少看了内容，日志一条没少 —— 所以之后还能回放、还能 fork。
自测压缩之后，被摘要掉的那几条还能找回来吗？

能。replace 只是让它们不再进入后续请求，原记录仍在日志里。 想把它们重新拿回来，就从压缩发生之前的那个位置 fork 一条新会话 —— 这也正是 fork 只需要「一个边界」的原因。

进程死了，日志还在

只追加的日志还有一个不太起眼的好处：崩溃之后，它自己就能说清「发生过什么」。 不需要额外的状态文件，也不需要优雅退出。

麻烦在于，事件是按发生顺序写的，而一次工具调用横跨三条事件：模型说要调、harness 记下 tool/call、结果写成 tool/result。进程如果死在中间，日志就会留下三种残缺： 模型声明了调用但没有 tool/call；有 tool/call 但没有结果； turn 没有关闭。

ToolCallRecovery 干的就是这件事：它从已提交事件里跟踪「还没有结果的请求」， 不额外保存任何状态。实时步骤、崩溃恢复、fork 种子构造共用同一套逻辑 —— 区别只在文案。

packages/core/session/src/repair.ts

TOOL_NOT_STARTED
  The tool call was interrupted before the Harness recorded it as started.
  Retry it if it is still needed.

TOOL_OUTCOME_UNKNOWN
  The tool call was interrupted after it was recorded, but no result was
  durably recorded. Its outcome is unknown. Decide whether to retry from the
  tool semantics: retry only if the operation is read-only or idempotent;
  if it may have side effects, first verify external state or ask the user.
  Do not retry blindly.

第二条文案长得反常，是刻意的。日志只能证明「启动了」，证明不了「执行到哪儿」—— 而工具可能有副作用。所以恢复策略不是替模型猜，而是要求它先去看外部状态： 只读或幂等的操作可以直接重试，有副作用的先查再动。

还有一个反直觉的约定：读到不认识的 type，而且这条事件没有 ignorable 标记，读取器必须拒绝重建整个会话，而不是跳过它。 因为一条看不懂的事件可能改变后面所有事件的解释方式。宁可报错让人来看， 也不要静默地还原出一个被掏空的会话 —— 默认「必需」，遗忘标记只会多报错，不会少数据。

fork 就建在这套机制上：ctx.sessions.fork(source, boundary?, childSessionId?) 复制包含切点的精确前缀，然后由 buildForkSeed 补上缺失的工具结果、 以 forked 为原因关闭未闭合的步骤和回合。inheritedEventCount 只统计复制过来的那段前缀 —— 收尾事件属于子会话自己。

这一节只要记住三行
  1. 崩溃恢复不靠「记住」，靠重放日志里没闭合的调用。
  2. 合成结果分两种：没启动（可以直接重试）和启动过但没结果（先验证外部状态）。
  3. 遇到不认识的类型又没有 ignorable，读取器拒绝重建 —— 宁可报错，不可静默丢事件。
自测日志里有一条 tool/call 却没有 tool/result，模型会被告知什么？

TOOL_OUTCOME_UNKNOWN：结果未知。并且会明确要求它不要盲目重试 —— 只读或幂等的操作可以直接重来，可能有副作用的先检查外部状态或询问用户。 另一种情况（模型声明了调用但没记 tool/call）是 TOOL_NOT_STARTED， 可以直接重试。

只追加的代价

只追加换来的东西很实在：任何一个过去的时刻都能精确重放；任何一段历史都能切出来 fork； 每个请求都能被独立重建 —— 因为 request/header 会把完整的请求封装 在变化时写成快照，而不是靠「当前配置」去猜。

代价也很实在，而且都能在源码里看到痕迹：

  • 存储只增。一次长会话的日志，远大于它此刻的上下文窗口 —— 被压缩掉的条目仍然躺着。所以 request/header 只在封装真正变化时才写新快照， 其余轮次继承最新的那份。
  • 格式会漂移。会话格式有版本号，读写双方还得就「哪些事件是必需的」达成一致。 ignorable 和 SESSION_FORMAT_VERSION 就是为这件事存在的。
  • 只有分支，没有树。当前只支持基于边界的 fork；pi 那种「任意消息都能长出子树」的条目树 被推迟了 —— 除非真有人需要比边界 fork 更强的能力。

最后一件容易误会的事：默认情况下会话只在内存里。持久化不是这个包做的， 而是由订阅 session/event 流的插件叠加。需要「确定已经落盘」这个屏障时， 得显式等 ctx.sessions.flush(session) —— 别假定延后写入已经排空。

这一节只要记住三行
  1. 只追加换来了回放、fork、审计，以及「每个请求都能被精确重建」。
  2. 代价是存储只增和格式兼容负担：ignorable 与格式版本就是为此存在。
  3. 只有 fork，没有会话树；持久化靠订阅 session/event 的插件，默认在内存。
自测装好 harness 直接跑，关掉进程后会话还在吗？

默认不在了。dsh-session 只在内存里持有 Session， 持久化由订阅 session/event 的插件负责。要确认已经落盘，等 ctx.sessions.flush(session)，而不是假设写入已经完成。
