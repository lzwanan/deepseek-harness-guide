第 4 章 · plugin 模型 — 4.1

一切皆插件，但插件分三种角色

仓库的一句话简介是 Everything is a Plugin。这句话的重点不是「全是插件」，而是「插件之间怎么打交道」——那一半才是架构。

底座是一个叫 cordis 的插件运行时。它提供三件事：一个所有插件共享的 ctx；把某个对象注册成服务的机制（服务挂在一个键上，比如 ctx.shell）；以及 inject —— 插件声明「我需要哪些键」，声明了还没就位的键，它的装载会挂起等待，而不是报错。

机制就这么多。真正让六十多个包能长期共存的，是包边界上的一条纪律：一项可替换的能力，要按变化速率拆成三种角色。这一章就用 shell 这条最完整的能力缝，把这条纪律看清楚。

这一节只要记住三行
  1. cordis 给了三样东西：共享的 ctx、按键注册的服务、inject 声明依赖。
  2. inject 的语义是「等」，不是「报错」——依赖没就位，装载挂起。
  3. 机制是通用的；包怎么拆，是仓库自己加的纪律，就是接下来三个角色。
自测插件 A 想用插件 B 注册的服务，A 需要 import B 的代码吗？

不需要。A 只声明 inject: ['那个键']，然后面向键的类型编程 —— 类型来自 Service Definition 包，不是来自 B。这就是为什么换掉 B（Provider）时，A 一行代码都不用改。

一项能力，三个角色

shell 执行是仓库里可替换能力中最完整的一条缝，拆成了四个包、三种角色。 先看图，再看每个角色在源码里的长相。

三个角色、四帧故事：注册 → 等待 → 接通 → 换实现。看第 ④ 帧：左边的包名换了，中间的键和右边的 schema 纹丝不动 —— 这就是拆这三个角色买到的东西。

Service Definition 拥有 ctx.<key> 这个键和全部词汇。它是一个抽象类，不是 TypeScript 接口 —— 因为它要作为运行时的服务类型被注册：

packages/shell/shell/src/index.ts · 有删节

declare module '@deepseek-ai/cordis' {
  interface Context {
    shell: ShellExecutor        // 这个键归本包所有
  }
}

export abstract class ShellExecutor extends Service {
  constructor(ctx: Context) {
    super(ctx, 'shell')         // 注册成 ctx.shell
  }
  abstract resolve(request: ShellExecRequest): ShellExecSpec
  abstract execute(spec: ShellExecSpec): Promise<ShellExecution>
}

Service Provider 提供实现：dsh-bash-local 用本地子进程实现这个抽象类，dsh-bash-sandbox 用沙箱实现它。装载哪个，ctx.shell 就是谁 —— 每个键同时只允许一个服务，装第二个会直接抛错。

Consumer 是模型和插件编程时面对的东西。dsh-tool-bash 声明自己依赖哪些键，然后只面向 Service Definition 的类型编程：

packages/shell/tool-bash/src/index.ts

export const inject = ['tools', 'shell', 'systemPrompt',
                       'shellEnv', 'workingDirectory']

// …装载完成后：
proc = await ctx.shell.execute({ ...spec, signal })

注意 Consumer 的依赖清单里没有任何 bash-local 的类型。它注入的是 shell 这个键 —— 键背后今天是本地子进程，明天换成沙箱，这一行 ctx.shell.execute(...) 一个字符都不用动。

这一节只要记住三行
  1. Definition 拥有键和词汇（抽象类）；Provider 提供实现；Consumer 面向键编程。
  2. 每个键同时只有一个服务 —— 重复装载同一个键会抛错，这是故意的。
  3. Consumer 的 inject 清单里永远不出现 Provider 的名字。
自测为什么 Service Definition 是抽象类而不是 interface？

因为它要在运行时被注册成服务（super(ctx, 'shell')），而不只是在编译期做形状检查。 接口编译后就不存在了，挂不到 ctx 上；抽象类既给出词汇和默认行为， 又强制 Provider 实现抽象方法 —— 一份代码同时服务两个角色。

换实现，不动约定

拆三个角色的理由写在设计笔记的第一段：约定、实现、消费方 API，这三样东西以不同的速率、因为不同的原因变化。 把它们捆在一个包里，换执行器就要连着动工具 schema —— 而模型看到的约定根本没变。

仓库里这条缝的现存证据，就是包的描述文字：

  • dsh-shell —— Abstract bash executor seam (ctx.shell)。 只有 3 个源码文件，没有任何「执行」的实现。
  • dsh-bash-local —— Local-subprocess implementation of the … bash executor seam。 子进程、超时、溢出文件，全是它的实现细节。
  • dsh-bash-sandbox —— Sandbox-consuming implementation of the … seam。 和 local 是兄弟包：实现同一个抽象类，互相不知道对方存在。
  • dsh-tool-bash —— Model-facing bash tool。 关心的只有 schema、后台任务和升级策略，不关心底下谁在跑。

反例同样重要：LLM 这条缝没有拆 —— Service Definition 和 Consumer 合在 dsh-llm 里，各家模型适配器作为 Provider 单独成包。因为它的 Consumer 是 agent loop 本身，不存在「可替换的 schema 接口」。设计笔记里写得很直白： 如果一项能力只想象得出一种 Provider 和一个 Consumer，就保持一个包，直到出现第二个 —— 不要预防性地拆。

这一节只要记住三行
  1. 拆包的依据是变化速率，不是「分层好看」。
  2. local 和 sandbox 是实现同一抽象类的兄弟包 —— 平级、互不感知。
  3. 只有一个 Provider 和一个 Consumer 的能力保持一个包（LLM 缝），拆分本身有成本。
自测换掉 dsh-bash-local 之后，模型的工具列表会变化吗？

不会。工具 schema 属于 Consumer（dsh-tool-bash），它注入的是 shell 这个键。Provider 换成沙箱后，模型看到的还是那个 bash 工具 —— 变的只是每条命令在底下怎么被关起来。

拿到包名，先定位角色

这一章最终要变成一个读代码的惯用动作：碰到仓库里任何一个包，先问它是三个角色中的哪一个， 然后顺着键往下走。按命中率排序，判断手段是：

  • 看 package.json 的描述。带 seam / Abstract 的是 Definition；带 implementation of 的是 Provider；带 Model-facing 的是 Consumer。
  • 看 src 里有没有 export const inject。有，就是 Consumer （或自带消费方的复合插件）；没有而 extends Service，就是 Definition。
  • 看 declare module 块给 Context 加了什么键 —— 那是这条缝在 ctx 上的地址，全仓库搜这个键就能找齐所有 Provider 和 Consumer。
  • 记住一条快捷路径：ctx.<key> → 键的类型在哪个包 → 那个包就是 Definition → 再搜谁 extends 它（Provider）、谁 inject 它（Consumer）。

下一章「能力缝」会用这套动作过一遍仓库里其余的缝 —— jobs、sandbox、mcp —— 你会发现它们全是同一个故事的变奏。

这一节只要记住三行
  1. 描述文字就是角色标签：seam / Abstract、implementation of、Model-facing。
  2. export const inject 和 extends Service 是比包名更可靠的判据。
  3. 顺着一个 ctx.<key> 能找齐整条缝：类型 → Provider → Consumer。
自测packages/shell/tool-bash 是三个角色中的哪个？依据是什么？

Consumer。两个依据：src/index.ts 第一行就写着 export const inject = ['tools', 'shell', …]；描述是 Model-facing bash tool。它不 extends Service、不注册任何键 —— 它消费键。
