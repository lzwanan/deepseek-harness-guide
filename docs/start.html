上手 / get started

先跑起来，再谈原理

这一页只有可执行的东西：两条启动命令、两个 20 行以内的文件、一张「改哪里」对照表。 全部命令与代码取自上游文档，逐字可用。

它还是 developer preview。上游 README 用整段大写写着 THERE WILL BE COMPATIBILITY-BREAKING CHANGES。 所以下面这些命令过几个月可能变 —— 变了就以仓库里的 README 为准。 这也正是第 07 章讲的那件事：内部随便改，只有日志格式不许动。

需要 Node 和 pnpm。如果只想看看它能干什么，第 01 步的 npx 一行就够； 想改代码，走「从源码」那条。

01 跑起来

最快的一条 · 不需要 clone

npx @deepseek-ai/dsh web

默认在 http://127.0.0.1:3080 起 Web UI，并自动打开浏览器。 加 --no-open 只起服务不开窗。这时候你说话、它调工具、日志落盘 —— 全景页那八步已经全在跑了。

从源码 · 要改代码走这条

git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web

pnpm run build 准备产物，pnpm dsh web 直接用产物启动、不会再编译。 改源码时用 pnpm run dev:web，它会在一个终端里编译、起服务、并跟着改。

最后那个 web 是形态，不是参数。同一个 dsh 换一个词就换一副外壳：

形态 怎么起 什么时候用
web dsh web 带界面的日常使用，也是读源码时的调试入口
headless dsh headless 跑一次就退出，适合脚本和 CI
sdk dsh --profile sdk 用 JSON-RPC 说话，给自己的程序调用
acp dsh acp 接编辑器的 Agent Client Protocol

这四个不是四个程序，是四份配置。第 06 章 讲过：一份 profile 就是「组合包 + 自己的 patch」叠出来的一棵树，换 profile 就是换树。

02 第一个插件

在 dsh 里，插件就是一个导出 apply 的模块。 框架加载它时把 ctx 递进来，你在 ctx 上登记能力。 没有基类、没有生命周期接口、没有注册表要填。

新建 · scratch-plugin/src/my-plugin.ts

import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}

然后告诉启动器「多插一行」。这就是第 06 章讲的 --patch：一份只做插入的 patch，不改任何已有条目。

新建 · scratch-plugin/cordis.yml · 路径必须是绝对路径

- insert:
    - id: hello
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'

启动

pnpm dsh web --patch ./scratch-plugin/cordis.yml

你会看到什么：终端在启动过程中打印一行 [hello-plugin] plugin loaded!，Web UI 照常打开。 二十行不到，你已经改了一个正在运行的 agent 的行为。

这一行之所以能生效，是因为第 04 章那个 ctx：它不是配置对象，是运行时。你登记在这个对象上的任何东西 —— 事件监听、工具、定时器 —— 都会在插件卸载时自动撤销。 你不需要写 removeListener，也不需要 clearInterval。

需要自己清理的资源，这样交回去

export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('heartbeat'), 5000)
    return () => clearInterval(timer)   // 插件卸载时执行
  })
}

03 第一个工具

插件能跑，但模型还看不见它。要让模型动手，得注册一个工具 —— 这就是第 05 章那个「模型只看到四样东西」的实际形状。

替换 my-plugin.ts

import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'greet-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: {
      name: { type: 'string', required: true, description: 'The name to greet' },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`
    },
  }))
}

重启，然后在界面对它说：Use the greet tool to greet Ada. 它会调用 greet，拿回 Hello, Ada!。

这段代码里有三个东西值得单独看，它们正好对应三章：

inject: ['tools']

不是注释，是依赖声明。工具注册表没就位之前，这个插件挂着等，不会报错。 第 04 章

parameters

defineTool 从它推出 args 的类型，并在执行前替你把模型给的参数校验一遍 —— 你在 execute 里拿到的已经是干净的。 第 05 章

return 值

返回的是规范值，不是给人看的字符串。给模型看的话由 render 负责， 给界面看的卡片是第三件事。分开之后，同一个结果才能既进提示词又进 UI。 第 05 章

生产级的参考实现是 packages/shell/tool-bash： 一个工具怎么带后台任务、怎么出终端卡片、怎么把超长输出溢出到文件，那里都有。 但它不是读的第一个文件 —— 先把上面这二十行跑通。

04 想改东西，先定位它属于哪一类

跑通之后，真正的问题是「我要的那个改动，落在哪」。这张表按变动频率排， 越靠上越安全、越靠下越要谨慎。

你想做的事 写在哪 为什么
加一个能力 新插件 + defineTool 循环不用动，工具表是配置出来的
让工具列表按条件变化 tools/pre-execute 钩子 在装配请求之前筛，比改工具本身稳
拦一次危险调用 ctx.tools.guard() 单调拒绝：后面的监听器没法把它改回允许
改一次对话的推进顺序 agent/* 事件 观察或拦截进行中的工作，不碰循环实现
改默认值 / 换实现 对应的那一层 patch 组合包跟版本、profile 跟项目、home 跟人
改「什么算一条事实」 先写持久化确认记录 日志格式是唯一被冻结的东西，改它要走流程

跑不起来的时候，先看这三处

启动即退终端只留一行非零退出码

通常是必填条目没起来：agent-loop、tool-executor-native 或某个应用入口。普通插件起不来只警告，必填条目起不来才拆整个应用 —— 所以退出码非零说明问题在骨架，不在你的插件。第 06 章

插件加载了，但模型看不见工具

九成是两件事：inject 漏了（ctx.tools 还不存在）， 或者 description / parameters 写得不合法导致工具没被登记。 先看启动日志里有没有你的工具名，再看这轮对话的可见工具是不是被钩子筛掉了。

路径找不到—— --patch 里的插件路径

必须是绝对路径。patch 文件只贡献配置，不会改变 loader 解析模块路径时用的目录。 相对路径在某些情况下能跑，但那不是它承诺的行为。
